PROJECT NAME
PeopleMatrix — Snapnet Cybersecurity Technical Assessment Lab

ROLE
Act as a senior full-stack software engineer, application-security engineer, DevSecOps engineer, and cybersecurity training-lab designer.

Build a complete, self-contained, intentionally vulnerable HR SaaS application called “PeopleMatrix”.

IMPORTANT CONTEXT
PeopleMatrix is NOT a production application.

It is an intentionally vulnerable cybersecurity training and recruitment-assessment application that will be used by Snapnet Limited to evaluate cybersecurity candidates in an authorised, isolated lab environment.

All users, employees, payroll information, NINs, bank accounts, emails, addresses and other records MUST be synthetic/fictitious.

The application must:
1. Look and behave like a realistic HR SaaS product.
2. Contain exactly eight deliberately planted security weaknesses described below.
3. Include realistic non-vulnerable functionality so candidates must investigate rather than simply scan obvious endpoints.
4. Support web and REST API penetration testing.
5. Be resettable between candidates.
6. Run completely through Docker Compose.
7. Never require real production credentials or external production systems.
8. Be suitable for deployment on an isolated AWS EC2 or Azure VM.
9. Include a separate assessor answer key that is never exposed through the candidate-facing application.
10. Include clear warnings that the application must not be exposed directly to the public Internet.

Do NOT introduce additional intentional vulnerabilities beyond the eight specified below.

7. DELIBERATELY PLANTED VULNERABILITIES
==================================================

IMPORTANT:

Implement exactly the following eight deliberate vulnerabilities.

Do not accidentally introduce additional vulnerabilities elsewhere.

Every vulnerability must:
- be reproducible;
- use synthetic data only;
- be documented privately in assessor/ANSWER_KEY.md;
- have a corresponding remediation documented;
- have an automated verification test for lab maintainers where practical.

----------------------------------------------
VULNERABILITY 1
BOLA / IDOR — PAYROLL API
----------------------------------------------

Create a broken object-level authorization vulnerability in:

GET /api/v1/employees/:id/payroll

Normal behaviour should allow an employee to retrieve their own payroll information.

However, deliberately make the vulnerable endpoint verify only that the requester is authenticated.

It should fail to verify that the requested employee ID belongs to the authenticated user or is otherwise authorised.

Example conceptual behaviour:

Employee 1048 legitimately requests:

GET /api/v1/employees/1048/payroll

and receives their payroll.

If they change 1048 to 1049, the vulnerable API should return employee 1049's synthetic payroll record.

Do NOT provide a bulk enumeration endpoint.

The candidate should discover and validate this manually.

Assessor classification:

Broken Object Level Authorization / IDOR.

Remediation:
Implement server-side object-level authorization based on authenticated identity and permitted relationships/roles.

----------------------------------------------
VULNERABILITY 2
BROKEN FUNCTION LEVEL AUTHORIZATION
----------------------------------------------

Endpoint:

POST /api/v1/admin/users

This endpoint is intended for SYSTEM_ADMIN only.

Deliberately implement authentication but omit the required server-side SYSTEM_ADMIN role authorization check for this specific endpoint.

A normal authenticated Employee should therefore be able to invoke the administrative function if they discover the endpoint.

The UI must NOT expose the System Administration menu to employees.

This forces candidates to distinguish UI restrictions from server-side authorization.

Remediation:
Implement explicit server-side RBAC/authorization middleware.

----------------------------------------------
VULNERABILITY 3
SQL INJECTION
----------------------------------------------

Create one deliberately vulnerable employee-search/filter endpoint.

For example:

GET /api/v1/employees/search?department=

Implement this specific endpoint using unsafe query construction so that its parameter is SQL injectable.

Keep all other database queries parameterized.

The vulnerability must exist only inside the isolated lab database.

The candidate should be able to manually establish that SQL injection exists without needing destructive operations.

Do NOT provide functionality that encourages destructive SQL commands.

Remediation:
Parameterized queries/prepared statements, input validation and least-privileged DB credentials.

----------------------------------------------
VULNERABILITY 4
STORED CROSS-SITE SCRIPTING
----------------------------------------------

Implement a stored XSS weakness in:

Performance Comments

A manager can enter a performance comment for an employee.

For this specific field, deliberately store and render the comment without appropriate output encoding/sanitization.

The vulnerable payload should execute when the affected performance record is viewed in the lab browser.

All other user-generated content should be safely encoded.

Remediation:
Context-sensitive output encoding/sanitization and appropriate Content Security Policy.

----------------------------------------------
VULNERABILITY 5
WEAK SESSION/TOKEN INVALIDATION
----------------------------------------------

Use JWT authentication.

Deliberately implement logout such that the client removes its local token but the server does not revoke or invalidate the issued token.

Therefore, a previously captured token should remain valid until expiration even after the user logs out.

Use a reasonable lab token lifetime.

Do NOT introduce weak JWT signing secrets or algorithm confusion.

The vulnerability being tested is specifically insufficient server-side session/token invalidation.

Remediation:
Appropriate token revocation/session management, short-lived access tokens and controlled refresh-token lifecycle.

----------------------------------------------
VULNERABILITY 6
EXCESSIVE DATA EXPOSURE
----------------------------------------------

Create an employee-profile API used by the frontend.

For a normal employee-directory request, deliberately return more information in the API response than the UI displays.

Example fields:

name
email
department
jobTitle

plus unnecessary:

salary
syntheticNIN
bankAccount
internalRole

The React UI should display only the normal directory fields.

The sensitive synthetic fields should nevertheless be visible in the underlying API response.

Remediation:
Server-side response DTOs/data minimization and field-level authorization.

----------------------------------------------
VULNERABILITY 7
SECURITY MISCONFIGURATION
----------------------------------------------

Introduce a limited set of related application-security misconfigurations that together count as ONE finding.

Use:

- verbose application error messages on one API route;
- unnecessary server/version information;
- one important missing browser security header.

Do NOT disable all security headers.

Do NOT introduce dangerous infrastructure-level configuration.

The candidate should recognise these as security-hardening issues rather than exaggerating their severity.

Remediation:
Production-safe error handling, removal of unnecessary version disclosure and appropriate security headers.

----------------------------------------------
VULNERABILITY 8
CONTROLLED FALSE POSITIVE / NON-EXPLOITABLE FINDING
----------------------------------------------

Create a condition likely to be flagged by an automated scanner but which is not practically exploitable in the implemented context.

The purpose is to determine whether candidates validate automated findings before reporting them.

Document exactly why it is a false positive/non-exploitable condition in assessor/ANSWER_KEY.md.

Do not make this ambiguous to the assessor.

The candidate should receive reduced marks if they report the scanner output as a confirmed high/critical vulnerability without validation.

8. SAFE FUNCTIONALITY
==================================================

The rest of the application should follow reasonable security practices.

Examples:

- password hashes using bcrypt or Argon2;
- parameterized database queries except the deliberate SQLi;
- RBAC except the deliberate BFLA;
- output encoding except the deliberate stored XSS;
- reasonable password policy;
- normal audit logging;
- no hard-coded production secrets;
- no command injection;
- no arbitrary file upload;
- no SSRF;
- no remote code execution;
- no path traversal;
- no insecure deserialization;
- no real third-party integrations.

This is important because the assessment should test the eight intended weaknesses rather than accidental coding defects.
